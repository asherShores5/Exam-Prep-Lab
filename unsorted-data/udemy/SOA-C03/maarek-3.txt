Correct answer

Overall explanation

Correct option:

Create a CloudWatch alarm for CPU Utilization of the Amazon EC2 instance, with detailed monitoring enabled. Configure an action to restart the instance when the alarm is triggered

CPUUtilization is an instance metric that is already defined with CloudWatch for monitoring Amazon EC2 instances.

By default, your instance is enabled for basic monitoring. You can optionally enable detailed monitoring. After you enable detailed monitoring, the Amazon EC2 console displays monitoring graphs with a 1-minute period for the instance. In Basic monitoring, data is available automatically in 5-minute periods at no charge. For Detailed monitoring, data is available in 1-minute periods for an additional charge.

If you enable detailed monitoring, you are charged per metric that is sent to CloudWatch. You are not charged for data storage.

You can enable detailed monitoring on an instance as you launch it or after the instance is running or stopped. Enabling detailed monitoring on an instance does not affect the monitoring of the EBS volumes attached to the instance.

Once the detailed monitoring is active, you can configure an action to restart the instance when the alarm is triggered based on the CPUUtilization metric.

Which of the following is the MOST cost-effective way of isolating the Amazon EC2 instances to a single tenant?

On-Demand Instances

Dedicated Hosts
Correct answer

Dedicated Instances

Spot Instances
Overall explanation

Correct option:

Dedicated Instances - Dedicated Instances are Amazon EC2 instances that run in a virtual private cloud (VPC) on hardware that's dedicated to a single customer. Dedicated Instances that belong to different AWS accounts are physically isolated at a hardware level, even if those accounts are linked to a single-payer account. However, Dedicated Instances may share hardware with other instances from the same AWS account that are not Dedicated Instances.

A Dedicated Host is also a physical server that's dedicated for your use. With a Dedicated Host, you have visibility and control over how instances are placed on the server.

Differences between Dedicated Hosts and Dedicated Instances:

via - https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/dedicated-hosts-overview.html#dedicated-hosts-dedicated-instances

Incorrect options:

Spot Instances - A Spot Instance is an unused EC2 instance that is available for less than the On-Demand price. Your Spot Instance runs whenever capacity is available and the maximum price per hour for your request exceeds the Spot price. Any instance present with unused capacity will be allocated. Even though this is cost-effective, it does not fulfill the single-tenant hardware requirement of the client and hence is not the correct option.

Dedicated Hosts - An Amazon EC2 Dedicated Host is a physical server with EC2 instance capacity fully dedicated to your use. Dedicated Hosts allow you to use your existing software licenses on EC2 instances. With a Dedicated Host, you have visibility and control over how instances are placed on the server. This option is costlier than the Dedicated Instance and hence is not the right choice for the current requirement.

On-Demand Instances - With On-Demand Instances, you pay for the compute capacity by the second with no long-term commitments. You have full control over its lifecycle—you decide when to launch, stop, hibernate, start, reboot, or terminate it. Hardware isolation is not possible and on-demand has one of the costliest instance charges and hence is not the correct answer for current requirements.

A large IT company uses several AWS accounts for the different lines of business. Quite often, the CloudOps Engineer is faced with the problem of sharing AWS KMS keys across multiple AWS accounts for accessing AWS resources spread across these accounts.

How will you implement a solution to address this issue?
Correct answer

The key policy for the KMS key must give the external account (or users and roles in the external account) permission to use the key. IAM policies in the external account must delegate the key policy permissions to its users and roles

Declare a key policy for the KMS Key to give the external account permission to use the KMS key. This key policy should be embedded with the first request of every transaction

Use AWS KMS service-linked roles to share access across AWS accounts

AWS Owned key can be used across AWS accounts. Configure an AWS Owned key and use it across accounts that need to share the key material
Overall explanation

Correct option:

The key policy for the KMS key must give the external account (or users and roles in the external account) permission to use the KMS key. IAM policies in the external account must delegate the key policy permissions to its users and roles

You can allow IAM users or roles in one AWS account to use a KMS key in a different AWS account. You can add these permissions when you create the KMS key or change the permissions for an existing KMS key.

To permit the usage of a KMS key to users and roles in another account, you must use two different types of policies:

    The key policy for the KMS key must give the external account (or users and roles in the external account) permission to use the KMS key. The key policy is in the account that owns the KMS key.

    IAM policies in the external account must delegate the key policy permissions to its users and roles. These policies are set in the external account and give permissions to users and roles in that account.

Incorrect options:

AWS Owned KMS key can be used across AWS accounts. Configure an AWS Owned KMS key and use it across accounts that need to share the key material - AWS owned KMS keys are a collection of KMS keys that an AWS service owns and manages for use in multiple AWS accounts. However, you cannot view, use, track, or audit them

Use AWS KMS service-linked roles to share access across AWS accounts - AWS Key Management Service uses AWS Identity and Access Management (IAM) service-linked roles. A service-linked role is a unique type of IAM role that is linked directly to AWS KMS. The service-linked roles are defined by AWS KMS and include all the permissions that the service requires to call other AWS services on your behalf. You cannot use AWS KMS service-linked roles to share access across AWS accounts.

Declare a key policy for the KMS key to give the external account permission to use the KMS key. This key policy should be embedded with the first request of every transaction - Key policy can not be directly shared across accounts.

Question 8Skipped

A company streams application logs to Amazon CloudWatch Logs. One of the log fields records application latency values. A CloudOps engineer must observe the 90th percentile (p90) latency trend over time by using native AWS monitoring capabilities.

Which solution should the CloudOps engineer implement to meet this requirement?

Create a CloudWatch Logs subscription filter that forwards the log data to Amazon Kinesis Data Firehose for percentile calculation

Enable CloudWatch Logs Insights queries on the log group and use a scheduled query to calculate the p90 latency value over time

Configure an Amazon CloudWatch Contributor Insights rule to analyze the latency field and track percentile based trends
Correct answer

Define a CloudWatch Logs metric filter that extracts the latency field and publishes it as a CloudWatch metric
Overall explanation

Correct option:

Define a CloudWatch Logs metric filter that extracts the latency field and publishes it as a CloudWatch metric

CloudWatch Logs metric filters allow numeric values to be extracted from log events and published as custom CloudWatch metrics. Once the latency field is emitted as a metric, CloudWatch can calculate statistics such as p90 over a defined time period. CloudWatch supports percentile statistics only on metrics, not directly on raw log events. By converting the latency field into a metric, the CloudOps engineer enables native percentile calculations and long term trend analysis.

This approach integrates cleanly with CloudWatch dashboards and alarms, requires minimal operational overhead, and aligns with CloudOps best practices for log based metric monitoring.

via - https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/MonitoringLogData.html

Incorrect options:

Configure an Amazon CloudWatch Contributor Insights rule to analyze the latency field and track percentile based trends - CloudWatch Contributor Insights is designed to identify top contributors and aggregate patterns across dimensions such as users or resources. It is optimized for analyzing distribution of contributors rather than calculating percentile statistics on numeric values. Contributor Insights does not support p90 or other percentile calculations on log fields. It cannot produce time series percentile metrics suitable for latency monitoring.

Create a CloudWatch Logs subscription filter that forwards the log data to Amazon Kinesis Data Firehose for percentile calculation - Subscription filters stream log data to external services for real time processing. While this enables custom analytics pipelines, it requires additional services to compute percentiles and store results. This approach introduces unnecessary complexity and operational overhead compared to using native CloudWatch metric filters. It does not directly satisfy the requirement to monitor p90 latency within CloudWatch.

Enable CloudWatch Logs Insights queries on the log group and use a scheduled query to calculate the p90 latency value over time - CloudWatch Logs Insights can calculate percentiles such as p90 within ad hoc queries, but it does not produce persistent CloudWatch metrics. Results exist only at query time and are not continuously tracked as time series metrics. Because Logs Insights queries are not native metrics, they cannot directly power CloudWatch alarms or long term dashboards for ongoing percentile monitoring. This approach does not meet the requirement to monitor p90 latency over time using CloudWatch metrics.

References:

https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/MonitoringLogData.html

https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/cloudwatch_concepts.html

A CloudOps engineer must implement automated alerting and remediation for a web application that runs on Amazon EC2 instances behind a load balancer. Each instance has SSM Agent installed and writes web server logs to local disk. The solution must detect specific error patterns in the logs and automatically restart the web server software when those errors occur.

Which actions do you suggest to meet these requirements? (Select three)

Configure the load balancer health check to fail when the error pattern occurs and rely on Auto Scaling to replace the instance automatically
Correct selection

Install and configure the Amazon CloudWatch agent on the EC2 instances to send the web server logs to CloudWatch Logs

Create a CloudWatch Logs Insights query that calculates the error count and use a scheduled query to trigger remediation when the error count exceeds a threshold

Configure an Amazon SNS notification action on the alarm and configure SNS to directly start an AWS Systems Manager Automation runbook that restarts the web server software
Correct selection

Create a CloudWatch Logs metric filter that matches the specific web error pattern and create a CloudWatch alarm based on the generated metric
Correct selection

Create an Amazon EventBridge rule that matches the CloudWatch alarm state change and configure the rule to start an AWS Systems Manager Automation runbook that restarts the web server software
Overall explanation

Correct options:

Install and configure the Amazon CloudWatch agent on the EC2 instances to send the web server logs to CloudWatch Logs

As the application writes logs locally on the EC2 instances, the solution must first centralize those logs in a service that supports near real time pattern detection. The CloudWatch agent can collect log files from the instances and publish them to CloudWatch Logs. Once logs land in CloudWatch Logs, the engineer can apply metric filters and alarms without building a separate log shipping pipeline. This keeps the design simple and reduces operational effort.

This step aligns with the requirement to detect specific web errors in logs and enables the remaining alerting and remediation components.

Create a CloudWatch Logs metric filter that matches the specific web error pattern and create a CloudWatch alarm based on the generated metric

CloudWatch Logs metric filters can match patterns in log events and turn matches into CloudWatch metrics. By defining a filter for the specific web error signature, the engineer can increment a metric whenever the error occurs. A CloudWatch alarm can then evaluate the metric over time and move to the ALARM state when the error rate crosses a threshold. This provides deterministic detection based on log content rather than indirect signals like CPU or HTTP 5xx at the load balancer.

This approach meets the requirement to detect specific web errors in the logs with minimal operational overhead because CloudWatch manages metric generation and alarm evaluation.

via - https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/MonitoringLogData.html

Create an Amazon EventBridge rule that matches the CloudWatch alarm state change and configure the rule to start an AWS Systems Manager Automation runbook that restarts the web server software

CloudWatch alarms emit state change events that Amazon EventBridge can match. By creating an EventBridge rule for the alarm transitioning to ALARM, the engineer can trigger remediation automatically. AWS Systems Manager Automation can run a runbook that restarts the web server software on the affected instances. Automation integrates cleanly with SSM Agent, supports controlled execution, and provides auditability through execution history.

This design is event driven, minimizes custom code, and satisfies the requirement for automatic restart when specific log errors are detected.

via - https://docs.aws.amazon.com/systems-manager/latest/userguide/systems-manager-automation.html

Incorrect options:

Configure the load balancer health check to fail when the error pattern occurs and rely on Auto Scaling to replace the instance automatically - Load balancer health checks can detect whether an instance responds to a configured endpoint, but they do not inspect local log files for specific error patterns. An instance can still pass health checks while the application logs show errors that require a restart. Replacing instances through Auto Scaling can restore capacity, but it is slower and more disruptive than restarting a web service process. It also fails the requirement to restart the web server software automatically based on log content.

Create a CloudWatch Logs Insights query that calculates the error count and use a scheduled query to trigger remediation when the error count exceeds a threshold - CloudWatch Logs Insights is excellent for interactive analysis and troubleshooting, but it does not provide a native, continuous alerting mechanism based on query results that directly triggers remediation in the same way metric filters and alarms do. Relying on scheduled queries adds operational complexity and increases detection latency compared to metric filters that evaluate log ingestion continuously. This does not best meet the requirement for automatic restart when errors are detected.

Configure an Amazon SNS notification action on the alarm and configure SNS to directly start an AWS Systems Manager Automation runbook that restarts the web server software - CloudWatch alarms can publish notifications to SNS, but SNS does not directly start Systems Manager Automation runbooks as a built in alarm action. You typically use EventBridge or a Lambda intermediary to initiate Automation based on an alarm. This option omits the required integration step that turns the alarm notification into an Automation execution. As written, it does not implement the remediation path needed to restart the web server software.

Correct answer

Trust policy
Overall explanation

Correct option:

You manage access in AWS by creating policies and attaching them to IAM identities (users, groups of users, or roles) or AWS resources. A policy is an object in AWS that, when associated with an identity or resource, defines their permissions. Resource-based policies are JSON policy documents that you attach to a resource such as an Amazon S3 bucket. These policies grant the specified principal permission to perform specific actions on that resource and define under what conditions this applies.

Trust policy - Trust policies define which principal entities (accounts, users, roles, and federated users) can assume the role. An IAM role is both an identity and a resource that supports resource-based policies. For this reason, you must attach both a trust policy and an identity-based policy to an IAM role. The IAM service supports only one type of resource-based policy called a role trust policy, which is attached to an IAM role.

Incorrect options:

AWS Organizations Service Control Policies (SCP) - If you enable all features of AWS organization, then you can apply service control policies (SCPs) to any or all of your accounts. SCPs are JSON policies that specify the maximum permissions for an organization or organizational unit (OU). The SCP limits permissions for entities in member accounts, including each AWS account root user. An explicit deny in any of these policies overrides the allow.

Access control list (ACL) - Access control lists (ACLs) are service policies that allow you to control which principals in another account can access a resource. ACLs cannot be used to control access for a principal within the same account. Amazon S3, AWS WAF, and Amazon VPC are examples of services that support ACLs.

Permissions boundary - AWS supports permissions boundaries for IAM entities (users or roles). A permissions boundary is an advanced feature for using a managed policy to set the maximum permissions that an identity-based policy can grant to an IAM entity. An entity's permissions boundary allows it to perform only the actions that are allowed by both its identity-based policies and its permissions boundaries.

A company runs a production database on an Amazon EC2 instance that uses Amazon EBS volumes for storage. During a disaster recovery exercise, the company must restore the most recent EBS snapshots to a new EC2 instance in a different Availability Zone. The restored EBS volumes must immediately deliver their full provisioned performance so that validation testing can begin without delay.


Which solution would you suggest to meet these requirements?

    Activate EBS Fast Snapshot Restore for the snapshots in the source Availability Zone. Create new EBS volumes in the target Availability Zone from the snapshots and attach the volumes to a new EC2 instance

    Configure the snapshots with Provisioned IOPS settings before creating new EBS volumes in the target Availability Zone and attach the volumes to a new EC2 instance

    Activate EBS Fast Snapshot Restore for the snapshots in the target Availability Zone. Create new EBS volumes in that Availability Zone from the snapshots and attach the volumes to a new EC2 instance

    Copy the EBS snapshots to the target Availability Zone before creating new EBS volumes and attach the volumes to a new EC2 instance

What's your guess? Scroll below for the answer





















Correct: 3.

Correct option:

Activate EBS Fast Snapshot Restore for the snapshots in the target Availability Zone. Create new EBS volumes in that Availability Zone from the snapshots and attach the volumes to a new EC2 instance

EBS Fast Snapshot Restore allows volumes created from a snapshot to immediately deliver their full provisioned performance. Without Fast Snapshot Restore, volumes lazily load data from Amazon S3, which can introduce latency during initial reads. Fast Snapshot Restore must be enabled in the specific Availability Zone where the restored volumes will be created. Enabling it in the target Availability Zone ensures that restored volumes do not experience performance degradation during initialization.

This configuration allows the company to begin validation testing immediately after volume creation, meeting the requirement for rapid recovery and full performance delivery.

Incorrect options:

Activate EBS Fast Snapshot Restore for the snapshots in the source Availability Zone. Create new EBS volumes in the target Availability Zone from the snapshots and attach the volumes to a new EC2 instance - Fast Snapshot Restore operates at the Availability Zone level. Enabling it in the source Availability Zone does not provide performance benefits when creating volumes in a different Availability Zone. Because the restored volumes will be created in the target Availability Zone, Fast Snapshot Restore must be enabled in that zone. This configuration does not meet the performance requirement.

Configure the snapshots with Provisioned IOPS settings before creating new EBS volumes in the target Availability Zone and attach the volumes to a new EC2 instance - Provisioned IOPS settings apply to EBS volumes, not to snapshots. Snapshots do not store performance configuration attributes. Even if the restored volume is created with Provisioned IOPS, it will still experience lazy loading unless Fast Snapshot Restore is enabled. This option does not eliminate initialization latency.

Copy the EBS snapshots to the target Availability Zone before creating new EBS volumes and attach the volumes to a new EC2 instance - EBS snapshots are stored in Amazon S3 at the Regional level and are not confined to a specific Availability Zone. Copying a snapshot is required only when moving it to another Region, not to another Availability Zone within the same Region. Even if a snapshot copy were performed, the restored volume would still experience lazy loading unless EBS Fast Snapshot Restore is enabled in the target Availability Zone.

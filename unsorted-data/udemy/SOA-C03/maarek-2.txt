Question 1Skipped

A CloudOps engineer is setting up an Amazon CloudFront distribution that requires HTTPS support by using an SSL/TLS certificate. The engineer must ensure that the certificate renews automatically without manual intervention.

Which actions should the CloudOps engineer take to meet this requirement? (Select two)
Correct selection

Request and associate an SSL/TLS certificate issued by AWS Certificate Manager with the CloudFront distribution
Correct selection

Validate the SSL/TLS certificate by using DNS validation

Enable automatic certificate rotation in the CloudFront distribution settings

Create a self-signed SSL/TLS certificate and upload it to AWS Certificate Manager. Associate the certificate with the CloudFront distribution to enable HTTPS

Use AWS Secrets Manager to store the SSL/TLS private key and certificate. Configure CloudFront to retrieve the certificate from Secrets Manager during renewal
Overall explanation

Correct options:

Request and associate an SSL/TLS certificate issued by AWS Certificate Manager with the CloudFront distribution

AWS Certificate Manager provides fully managed SSL and TLS certificates that integrate directly with Amazon CloudFront. When a certificate is issued by ACM and associated with a CloudFront distribution, AWS manages the certificate lifecycle automatically. ACM handles certificate renewal before expiration without requiring any manual action from the CloudOps engineer. This removes operational overhead and eliminates the risk of certificate expiry causing service disruption.

Using ACM is a recommended best practice for CloudFront HTTPS configurations because it provides seamless integration, high availability, and automated lifecycle management.

Validate the SSL/TLS certificate by using DNS validation

DNS validation enables AWS Certificate Manager to automatically validate and renew certificates without relying on human interaction. Once the DNS validation record is created and remains in place, ACM can revalidate ownership during renewal cycles automatically. This method is particularly suitable for CloudFront distributions because certificates must reside in the us east 1 Region, and DNS validation works consistently across Regions and renewal periods.

DNS validation ensures uninterrupted certificate renewal and aligns with the requirement for automatic lifecycle management in production CloudOps environments.

via - https://docs.aws.amazon.com/acm/latest/userguide/domain-ownership-validation.html

Incorrect options:

Create a self-signed SSL/TLS certificate and upload it to AWS Certificate Manager. Associate the certificate with the CloudFront distribution to enable HTTPS - Self-signed certificates are not trusted by public browsers and are not suitable for production CloudFront distributions. CloudFront requires certificates issued by a trusted certificate authority for HTTPS connections. In addition, AWS Certificate Manager does not manage renewal for self-signed certificates. This approach fails to meet both the trust and automatic renewal requirements.

Enable automatic certificate rotation in the CloudFront distribution settings - Amazon CloudFront does not provide a configuration setting that automatically renews certificates. Certificate renewal is handled by the certificate authority, not by the CloudFront service itself. Relying on a non existent CloudFront feature can result in expired certificates and service outages. Certificate lifecycle management must be addressed through ACM configuration.

Use AWS Secrets Manager to store the SSL/TLS private key and certificate. Configure CloudFront to retrieve the certificate from Secrets Manager during renewal - AWS Secrets Manager is designed for storing secrets such as credentials, API keys, and tokens. It does not integrate with CloudFront for SSL or TLS certificate lifecycle management. CloudFront cannot retrieve certificates dynamically from Secrets Manager, and Secrets Manager does not provide certificate issuance or renewal capabilities. This solution does not satisfy the requirement for automatic certificate renewal.

However, AWS Health events from the linked member accounts do not trigger notifications in the payer account.

AWS Health must be configured only in the payer account, and it automatically consolidates all events from linked accounts once enabled
Correct answer

The organization must enable AWS Health organizational view through AWS Organizations to aggregate and monitor Health events across accounts

AWS Health events are account specific and are not automatically aggregated from linked member accounts into the payer account

Enable Amazon CloudWatch cross-account observability in the payer account to aggregate and monitor AWS Health events from all linked accounts
Overall explanation

Correct option:

The organization must enable AWS Health organizational view through AWS Organizations to aggregate and monitor Health events across accounts

AWS Health events are scoped to individual AWS accounts by default. In a multi account environment, each account receives its own AWS Health events unless organizational view is enabled. To centrally monitor Health events across accounts, the organization must enable AWS Health organizational view using AWS Organizations. This feature allows a delegated administrator or the management account to view and aggregate Health events from member accounts.

Without enabling organizational view, EventBridge rules in the payer account will not receive Health events from linked accounts. Enabling AWS Organizations integration is required for centralized monitoring.

Incorrect options:

AWS Health must be configured only in the payer account, and it automatically consolidates all events from linked accounts once enabled - Simply configuring AWS Health monitoring in the payer account does not automatically consolidate events from linked accounts. Organizational view must be explicitly enabled. Without enabling integration with AWS Organizations, the payer account can see only its own Health events. This option incorrectly assumes automatic aggregation behavior.

AWS Health events are account specific and are not automatically aggregated from linked member accounts into the payer account - AWS Health events are indeed account specific by default. However, AWS provides a supported mechanism to aggregate events across accounts through AWS Organizations. The alerts failed not because aggregation is impossible, but because the required organizational configuration was not enabled. This option describes the default behavior but does not identify the missing configuration step.

Enable Amazon CloudWatch cross-account observability in the payer account to aggregate and monitor AWS Health events from all linked accounts - CloudWatch cross-account observability enables centralized visibility for metrics, logs, and traces across multiple accounts. However, AWS Health events are delivered through EventBridge and require AWS Health organizational view for aggregation. Cross-account observability does not automatically aggregate AWS Health events from linked accounts. This option does not address the root cause of missing Health notifications.

Your home-cooking website stores its recipes and comments from users in a Multi-AZ RDS database, which is located in a private subnet. As of yesterday, it seems that your users are unable to access the website and see an error message "512 - Cannot connect to the database".

Overall explanation

Correct options:

DB Security Group inbound rules have changed

A security group acts as a virtual firewall that controls the traffic for one or more instances. When you launch an instance, you can specify one or more security groups; otherwise, we use the default security group. You can add rules to each security group that allows traffic to or from its associated instances. You can modify the rules for a security group at any time; the new rules are automatically applied to all instances that are associated with the security group. When we decide whether to allow traffic to reach an instance, we evaluate all the rules from all the security groups that are associated with the instance.

The following are the characteristics of security group rules:

By default, security groups allow all outbound traffic.

Security group rules are always permissive; you can't create rules that deny access.

Security groups are stateful

For the given use-case, if the DB Security Group inbound rules have changed, then the website may not be able to connect to the database.

Network ACL inbound rules have changed

Network ACL outbound rules have changed

A network access control list (ACL) is an optional layer of security for your VPC that acts as a firewall for controlling traffic in and out of one or more subnets. You might set up network ACLs with rules similar to your security groups in order to add an additional layer of security to your VPC.

The following are the basic things that you need to know about network ACLs:

The default NACL allows all inbound and outbound IPv4 traffic and, if applicable, IPv6 traffic.

You can create a custom network ACL and associate it with a subnet. By default, each custom network ACL denies all inbound and outbound traffic until you add rules.

Each subnet in your VPC must be associated with a network ACL. If you don't explicitly associate a subnet with a network ACL, the subnet is automatically associated with the default network ACL.

You can associate a network ACL with multiple subnets. However, a subnet can be associated with only one network ACL at a time. When you associate a network ACL with a subnet, the previous association is removed.

A network ACL contains a numbered list of rules. AWS evaluates the rules in order, starting with the lowest numbered rule, to determine whether traffic is allowed in or out of any subnet associated with the network ACL. The highest number that you can use for a rule is 32766. AWS recommends that you start by creating rules in increments (for example, increments of 10 or 100) so that you can insert new rules where you need to later on.

A network ACL has separate inbound and outbound rules, and each rule can either allow or deny traffic.

Network ACLs are stateless, which means that responses to allowed inbound traffic are subject to the rules for outbound traffic (and vice versa).

For the given use-case, if the inbound or the outbound NACL rules have changed, then the website may not be able to connect to the database.

Incorrect options:

Security Group outbound rules have changed - Since security groups are stateful so incoming connections can send a reply back to, regardless of any outbound rules, so this option is incorrect.

The primary database's private IP has changed - The private IP associated with an RDS database can change due to things such as multi-AZ failover, so you should use the DNS endpoint to connect to the database. Even if the private IP of the database changes, the DNS endpoint would not change on its own. So this option is incorrect.

A read replica has been created recently - Adding a read replica does not change the primary database's DNS name, so this option is ruled out.

Because the return traffic is being rejected, the subnet network ACL must be updated to allow outbound ICMP traffic destined for the on premises IP range. This resolves the ping failure.

Correct answer

Overall explanation

Correct options:

Convert the DB instance to a Multi-AZ deployment to enable synchronous replication and automatic failover

Multi-AZ deployments for Amazon RDS use synchronous replication to maintain a standby instance in a separate Availability Zone. When the primary instance fails, RDS automatically performs a failover to the standby. Because replication is synchronous, committed transactions are written to both the primary and standby before acknowledgment. This ensures that no committed transactions are lost during failover.

Multi-AZ provides automatic failover without manual intervention or custom scripting. It is specifically designed for high availability and disaster recovery within a Region.

Incorrect options:

Configure an RDS read replica in the same Region and automate promotion to primary by using an AWS Lambda function during a failure event - Read replicas use asynchronous replication. Transactions that are committed on the primary might not yet be replicated to the replica at the time of failure. Manual promotion through Lambda does not provide automatic failover with zero data loss. It also introduces operational complexity and recovery delays. This approach does not meet the requirement to avoid losing committed transactions.

Enable automated backups with a short backup retention period and perform a point in time restore to a new DB instance during a disaster recovery event - Automated backups and point in time restore allow recovery to a specific timestamp within the retention window. However, restoration requires creating a new DB instance and manually redirecting application traffic. Point in time restore does not provide automatic failover and cannot guarantee zero data loss because replication to backup storage is not synchronous at commit time. This approach does not meet the requirement for automatic failover without losing committed transactions.

Configure an RDS read replica in a secondary Region and automate promotion to primary by using an AWS Lambda function during a failure event - Cross Region read replicas are designed for disaster recovery and global read scaling. However, replication remains asynchronous across Regions. Network latency increases replication lag, which increases the risk of losing recently committed transactions during failover. Correct options:

A scaling policy instructs Amazon EC2 Auto Scaling to track a specific CloudWatch metric, and it defines what action to take when the associated CloudWatch alarm is in ALARM. The metrics that are used to trigger an alarm are an aggregation of metrics coming from all of the instances in the Auto Scaling group. (For example, let's say you have an Auto Scaling group with two instances where one instance is at 60 percent CPU and the other is at 40 percent CPU. On average, they are at 50 percent CPU.) When the policy is in effect, Amazon EC2 Auto Scaling adjusts the group's desired capacity up or down when the alarm is triggered.

via - https://docs.aws.amazon.com/autoscaling/ec2/userguide/as-scale-based-on-demand.html

Your ASG is at maximum capacity already

If your ASG is already at the maximum capacity, then it will not lead to a scale out action.

Your ASG Launch process has been suspended

For Amazon EC2 Auto Scaling, there are two primary process types: Launch and Terminate. The Launch process adds a new Amazon EC2 instance to an Auto Scaling group, increasing its capacity. The Terminate process removes an Amazon EC2 instance from the group, decreasing its capacity.

If the Launch process is suspended, then your Auto Scaling group does not scale out for alarms or any scheduled actions that occur.

Overall explanation

Correct option:

Enable Stickiness on the Application Load Balancer - By default, an Application Load Balancer routes each request independently to a registered target based on the chosen load-balancing algorithm. However, you can use the sticky session feature (also known as session affinity) to enable the load balancer to bind a user's session to a specific target. This ensures that all requests from the user during the session are sent to the same target. This feature is useful for servers that maintain state information in order to provide a continuous experience to clients. To use sticky sessions, the client must support cookies.

Application Load Balancers support both duration-based cookies and application-based cookies. The key to managing sticky sessions is determining how long your load balancer should consistently route the user's request to the same target. Sticky sessions are enabled at the target group level. You can use a combination of duration-based stickiness, application-based stickiness, and no stickiness across all of your target groups.

Incorrect options:

Enable Cookies on all the Application Load Balancer targets - Cookies are enabled on the client-side and not on the server-side.

Enable Connection Draining on the Application Load Balancer - To ensure that a Load Balancer stops sending requests to instances that are de-registering or unhealthy, while keeping the existing connections open, use connection draining. This enables the load balancer to complete in-flight requests made to instances that are de-registering or unhealthy. When you enable connection draining, you can specify a maximum time for the load balancer to keep connections alive before reporting the instance as de-registered.

Enable X-Forwarded-For header which can be used to store cookies on the server - The X-Forwarded-For request header is automatically added and helps you identify the IP address of a client when you use an HTTP or HTTPS load balancer. Because load balancers intercept traffic between clients and servers, your server access logs contain only the IP address of the load balancer. To see the IP address of the client, use the X-Forwarded-For request header.

A company runs a production database on an Amazon EC2 instance that uses Amazon EBS volumes for storage. During a disaster recovery exercise, the company must restore the most recent EBS snapshots to a new EC2 instance in a different Availability Zone. The restored EBS volumes must immediately deliver their full provisioned performance so that validation testing can begin without delay.


Which solution would you suggest to meet these requirements?

    Activate EBS Fast Snapshot Restore for the snapshots in the source Availability Zone. Create new EBS volumes in the target Availability Zone from the snapshots and attach the volumes to a new EC2 instance

    Configure the snapshots with Provisioned IOPS settings before creating new EBS volumes in the target Availability Zone and attach the volumes to a new EC2 instance

    Activate EBS Fast Snapshot Restore for the snapshots in the target Availability Zone. Create new EBS volumes in that Availability Zone from the snapshots and attach the volumes to a new EC2 instance

    Copy the EBS snapshots to the target Availability Zone before creating new EBS volumes and attach the volumes to a new EC2 instance

What's your guess? Scroll below for the answer





















Correct: 3.

Correct option:

Activate EBS Fast Snapshot Restore for the snapshots in the target Availability Zone. Create new EBS volumes in that Availability Zone from the snapshots and attach the volumes to a new EC2 instance

EBS Fast Snapshot Restore allows volumes created from a snapshot to immediately deliver their full provisioned performance. Without Fast Snapshot Restore, volumes lazily load data from Amazon S3, which can introduce latency during initial reads. Fast Snapshot Restore must be enabled in the specific Availability Zone where the restored volumes will be created. Enabling it in the target Availability Zone ensures that restored volumes do not experience performance degradation during initialization.

This configuration allows the company to begin validation testing immediately after volume creation, meeting the requirement for rapid recovery and full performance delivery.

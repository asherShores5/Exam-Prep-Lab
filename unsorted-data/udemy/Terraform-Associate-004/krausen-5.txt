Your Terraform configuration creates a VMware virtual machine. You want to ensure that the VM is created with at least 4 GB of memory, and if someone tries to create it with less, Terraform should fail before attempting creation. Which approach is correct? (select two)
Correct selection

Add a validation block to the variable, such as:


    validation {
      condition     = var.memory >= 4096
      error_message = "Memory must be at least 4096 MB."
    }

Explanation

Adding a validation block to the variable allows you to enforce constraints on the values that can be assigned to the variable. By specifying a condition that the memory must be at least 4 GB, Terraform will validate the input value and fail with an error if the condition is not satisfied.
Correct selection

Add a lifecycle block with a precondition to the resource, such as:


    lifecycle {
      precondition {
        condition     = var.memory >= 4096
        error_message = "Memory must be at least 4096 MB."
      }
    }

Explanation

Adding a lifecycle block with a precondition to the resource ensures that Terraform checks the condition before attempting to create the VMware virtual machine. If the condition, in this case, the memory being at least 4 GB, is not met, Terraform will fail with the specified error message before proceeding with the creation.

Add a check block to the configuration, such as:


    check "memory_check" {
      assert {
        condition     = var.memory >= 4096
        error_message = "Memory must be at least 4096 MB."
      }
    }

Explanation

Adding a check block to the configuration is not the correct approach for enforcing constraints on resource creation. The check block is used for defining custom validation rules for configurations, but it does not directly impact the creation of the VMware virtual machine with the required memory size.

Add a lifecycle block with a postcondition to the resource, such as:


    lifecycle {
      postcondition {
        condition     = self.memory >= 4096
        error_message = "Memory must be at least 4096 MB."
      }
    }

Explanation

Adding a lifecycle block with a postcondition to the resource is not the correct approach in this scenario. Postconditions are checked after the resource has been created, which means that the VM would already be created before the condition is verified. This does not prevent the creation of the VM with less than 4 GB of memory.
Overall explanation

Objective 4g - Validate configuration using custom conditions

Preconditions are evaluated before Terraform attempts to create or modify a resource. They're ideal for validating that input values or dependencies meet requirements before resource operations begin. A precondition in the VM resource's lifecycle block with condition = var.memory >= 4096 ensures the memory value is sufficient before Terraform attempts to create the VM. If the condition is false, Terraform errors with your custom message and doesn't attempt the creation.

Objective 4c - Use variables and outputs

Input variables (commonly referenced as just 'variables') are often declared in a separate file called variables.tf, although this is not required. Most people will consolidate variable declarations in this file for better organization and management simplification. Each variable used in a Terraform configuration must be declared before it can be used. Variables are declared in a variable block - one block for each variable. The variable block contains the variable name, most importantly, and then often includes additional information such as the type, a description, a default value, and other options.

The value of a Terraform variable can be set multiple ways, including setting a default value, interactively passing a value when executing a terraform plan and apply, using an environment variable, or setting the value in a .tfvars file. Each of these different options follows a strict order of precedence that Terraform uses to set the value of a variable.

A huge benefit of using Terraform is the ability to reference other resources throughout your configuration for other functions. These might include getting certain values needed to create other resources, creating an output to export a specific value, or using data retrieved from a data block. Most of these use dot-separated paths for elements of object values.

The following represents the kinds of named values available in Terraform:

    * <RESOURCE TYPE>.<NAME> represents a managed resource of the given type and name.

    * var.<NAME> is the value of the input variable of the given name.

    * local.<NAME> is the value of the local value of the given name.

    * module.<MODULE NAME> is a value representing the results of a module block.

    * data.<DATA TYPE>.<NAME> is an object representing a data resource of a given type and name

    * Additional named values include ones for filesystem and workspace info and block-local values

This mechanism maintains state file integrity and prevents conflicts that could result in infrastructure inconsistencies or corruption.

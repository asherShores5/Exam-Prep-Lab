Your organization uses Chef to configure application settings and install software packages on existing servers. The DevOps team is evaluating whether to adopt Terraform alongside Chef. Which statement best explains how Infrastructure as Code tools, like Terraform, differ from configuration management tools?

Infrastructure as Code tools can only create cloud resources and virtual machines, while configuration management tools can create both cloud and on-premises resources, including physical hardware.
Explanation
Infrastructure as Code tools, such as Terraform, have the capability to create and manage resources in cloud environments, like AWS or Azure, as well as virtual machines. They are not limited to cloud resources only. On the other hand, configuration management tools, like Chef, focus on configuring and managing software on existing servers, regardless of whether they are in the cloud or on-premises.

Infrastructure as Code tools use imperative programming models to define step-by-step infrastructure changes, while configuration management tools use declarative models for desired state.
Explanation

Infrastructure-as-Code tools, such as Terraform, employ a declarative approach to define the desired state of the infrastructure. This means specifying the end state of the infrastructure without detailing the step-by-step process to get there. On the other hand, configuration management tools, such as Chef, typically employ an imperative approach, focusing on defining the specific steps required to achieve a desired configuration state on servers.
Correct answer

Infrastructure as Code tools focus on provisioning and managing the lifecycle of infrastructure resources, while configuration management tools focus on installing and managing software on existing servers.
Explanation

Infrastructure as Code tools, like Terraform, are focused on defining and managing the infrastructure resources themselves, such as virtual machines, networks, and storage, by using code. On the other hand, configuration management tools, such as Chef, are primarily used for configuring and managing software and settings on existing servers. While both tools can be used together, they serve different purposes in the overall infrastructure management process.

Infrastructure as Code tools use agentless architectures to communicate with cloud providers, while configuration management tools always require agents to be installed on target systems.
Explanation

Infrastructure-as-Code tools, such as Terraform, do not necessarily rely on agents to communicate with cloud providers. They interact directly with APIs provided by cloud services to provision and manage resources. Configuration management tools, such as Chef, may require agents to be installed on target systems to execute configuration tasks. The use of agents is not a defining factor in distinguishing between Infrastructure as Code and configuration management tools.
Overall explanation

Objective 1b - Describe the advantages of IaC patterns

While both Infrastructure as Code and configuration management tools help automate IT operations, they serve complementary purposes. IaC tools like Terraform excel at provisioning infrastructure resources (such as networks, compute instances, and storage) and managing their lifecycle through creation, updates, and deletion. Configuration management tools, such as Chef, Puppet, or Ansible, focus on the ongoing configuration of software and services on existing infrastructure. Many organizations use both approaches together - Terraform to provision the infrastructure and configuration management tools to configure the applications running on that infrastructure.

      # ...
      tags = {
        ship  = "millennium-falcon"
        pilot = "han"
        droid = "r2d2"
        base  = "tatooine"
      }
     
      lifecycle {
        # WHAT GOES HERE?
      }
    }

    lifecycle {
      create_before_destroy = true
    }

Explanation

The create_before_destroy attribute in the lifecycle configuration is used to ensure that a new resource is created before the existing one is destroyed. This is not relevant to the requirement of ignoring future tag changes made by the bot while still considering tags at create time.

    lifecycle {
      ignore_changes = [tags["droid"]]
    }

Explanation

Using ignore_changes with a specific tag key like tags["droid"] would only ignore changes to that specific tag key. In this scenario, the requirement is to ignore any changes to tags in general, not just a specific tag key.     lifecycle {
      replace_triggered_by = [aws_iam_role.bot]
    }

The replace_triggered_by attribute in the lifecycle configuration is used to specify a list of resources that trigger a replacement of the current resource.     lifecycle {
      ignore_changes = [tags]
    }

By using the ignore_changes attribute with the tags key in the lifecycle configuration, Terraform will ignore any changes made to the tags after the resource is created. This ensures that Terraform will not attempt to update the tags if they are changed by the tag management bot, while still considering the tags during the initial creation of the resource.

Matthew wants to assign a value to a Terraform variable by using environment variables.

What is the correct format for naming the environment variable that should be set?

VAR_TF_NAME
Explanation

This format does not follow the specific naming convention required by Terraform to automatically recognize an environment variable as an input variable. Terraform looks for a specific prefix, and VAR_TF is not that prefix. If you set this, Terraform will simply ignore it during the plan or apply phase.

TF_VAR
Explanation

While TF_VAR is the correct prefix, it is incomplete on its own. Terraform requires the prefix to be followed immediately by the specific name of the variable defined in your configuration (e.g., TF_VAR_region). Setting an environment variable named just TF_VAR does nothing.

TF_VAR_ENV_name
Explanation

This is not the standard syntax unless your variable inside the Terraform configuration is explicitly named ENV_name. Terraform does not require an ENV middle segment. It strictly maps the string after the TF_VAR_ prefix directly to the variable name declared in your .tf files.
Correct answer

TF_VAR_name
Explanation

This is the standard convention. Terraform searches the environment for any variables starting with TF_VAR_ followed by the name of a declared variable. If you have a variable block variable "name" {}, setting the environment variable TF_VAR_name will successfully assign a value to it.
Overall explanation

To map an environment variable to a Terraform variable, you must use the prefix TF_VAR_ followed by the exact name of the variable as defined in your configuration. For example, if your Terraform code contains:

    variable "instance_count" {
      type = number
    }

You would set the environment variable in your shell like this: export TF_VAR_instance_count=5

Terraform automatically detects this prefix and injects the value 5 into the instance_count variable at runtime.

If John runs the terraform init command 10 times within a particular Terraform project directory, could this cause any corruption or alteration of the Terraform configuration files?

Yes
Explanation

This answer is incorrect because terraform init is designed to be an idempotent and safe operation. It does not modify your .tf configuration files (like main.tf or variables.tf). Running it multiple times simply ensures that the working directory is initialized, providers are downloaded, and the backend is configured, without changing the logic of your infrastructure code.
Correct answer

No
Explanation

terraform init is a non-destructive command used to initialize a working directory containing Terraform configuration files. You can run it as many times as you like; if the directory is already initialized and no changes have been made to provider requirements or backend configuration, the command effectively does nothing.
Overall explanation

In Terraform, the init command is the first command that should be run after writing a new Terraform configuration or cloning an existing one from version control. Its primary jobs are to:

    Initialize the backend (where state is stored).

    Download necessary provider plugins (like AWS, Azure, etc.).

    Download modules.

It is strictly a "read and setup" operation regarding your source code. It creates a hidden .terraform directory to store plugins and modules, but it never alters the actual .tf files you have written. Therefore, running it 10 times or 100 times is perfectly safe and will not corrupt your configuration.

True
Explanation

While they share the same name ("Workspaces") and a similar high-level goal (separating state), their implementation and scope are fundamentally different. In Terraform OSS (CLI), workspaces are just different state files within the same backend. Explanation

Terraform Cloud Workspaces act as complete environments that manage the entire lifecycle of a configuration, including variables, secrets, and run triggers. For students learning Terraform, this is a common point of confusion due to the naming collision.

Question 9Skipped

Matthew has created a map variable that stores several AMI IDs, each corresponding to a specific region. Here’s an example of the code:

    variable "ami_ids" {
       type = "map"
       default = {
           "mumbai" = "image-abc"
           "germany" = "image-def"
           "states"  = "image-xyz"
        }
    }

The goal is to select the value "image-def". Which of the following methods would you use to retrieve this image from the map?

var.ami_ids[1]
Explanation

Maps in Terraform are unordered collections of key-value pairs, not ordered lists or arrays. Therefore, you cannot access elements using numerical indices like [1]. Attempting to do so will result in an error because the key 1 does not exist in the map definition.

var.ami_ids[2]
Explanation

Similar to option A, this attempts to access the map using a numerical index, which is invalid for map data structures unless the keys themselves are numbers. Since the keys are strings ("mumbai", "germany", "states"), Terraform will look for a key literally named 2, fail to find it, and throw an error.

var.ami_ids["image-def"]
Explanation

This syntax attempts to look up a value by using the value itself as the key. In a map lookup, you must provide the unique identifier (the key) to retrieve the data associated with it. "image-def" is the data you want to retrieve, not the label used to find it.
Correct answer

var.ami_ids["germany"]
Explanation

To retrieve a specific value from a map variable in Terraform, you must reference the variable name followed by the specific key enclosed in square brackets and quotes. Since the key "germany" corresponds to the value "image-def" in the default block, this syntax successfully returns the desired image ID.
Overall explanation

In Terraform, a map is a data structure used to store values identified by string keys. Think of it like a dictionary where you look up a word (the key) to find its definition (the value).

    The Variable: var.ami_ids is the collection.

    The Key: "germany" is the unique label.

    The Value: "image-def" is the data stored under that label.

To access data in a map, you always use the syntax var.variable_name["key_name"]. You cannot use numerical positions (like 0, 1, 2) because maps do not guarantee order, and you cannot look up a key by providing the value. Therefore, var.ami_ids["germany"] is the only valid way to extract "image-def".

Question 11Skipped

Which Terraform files should be ignored by Git when committing code to a repository? (Choose Three)

variables.tf
Explanation

This file defines the input variables required for your infrastructure. It contains the schema and default values, not sensitive data. It is essential for anyone cloning the repository to understand how to configure the module, so it must be committed to Git.

output.tf
Explanation

This file defines the data that is returned by your Terraform module after execution (e.g., IP addresses, resource IDs). Like input definitions, output definitions are part of the infrastructure code logic and schema. Therefore, this file must be committed to Git so other users or modules can utilize these outputs.
Correct selection

Files named exactly terraform.tfvars or terraform.tfvars.json.
Explanation

These files are automatically loaded by Terraform to populate variables. They often contain environment-specific configurations, secrets, passwords, or API keys. Because they frequently house sensitive data or local configurations that shouldn't be shared across the entire team, they should be ignored by Git to prevent security leaks.
Correct selection

terraform.tfstate
Explanation

This file stores the mapping between your real-world resources and your configuration, often including sensitive data in plain text. Committing this file can lead to state conflicts (if multiple people apply changes) and severe security breaches. State should be stored in a remote backend (like S3 or Terraform Cloud), never in the Git repository.
Correct selection

Any files with names ending in .auto.tfvars or .auto.tfvars.json.
Explanation

Like terraform.tfvars, these files are automatically loaded by Terraform to set variable values. They are treated with the same security caution because they are prime locations for hardcoded secrets or local overrides. Standard .gitignore templates for Terraform almost always exclude these patterns to prevent accidental secret exposure.
Overall explanation

When managing Terraform with Git, the golden rule is to commit the code but ignore the data and secrets.

    Commit the Logic: You must commit files that define what to build (main.tf, variables.tf, outputs.tf, providers.tf). Without these, the code cannot run.

    Ignore the Secrets: Variable definition files (terraform.tfvars, *.auto.tfvars) often contain passwords, keys, and specific environment settings. Committing these exposes secrets to anyone with repo access.

    Ignore the State: The terraform.tfstate file is the "source of truth" for your live infrastructure. It contains sensitive data in plain text and changes every time you run an apply. It belongs in a secure Remote Backend (like AWS S3 with locking), not in version control.

Matthew wants to deploy two EC2 instances across two different AWS regions using Terraform. In his providers.tf file, he has the following configuration:


    provider "aws" { region = "us-east-1" }

However, when he runs terraform plan, he encounters an error. What steps should Matthew take to resolve this issue?

There cannot be two different AWS provider configuration in same file.
Explanation

You absolutely can have multiple provider configurations for the same provider (AWS, Azure, etc.) in the same file or module. This is a standard practice for multi-region or multi-account deployments. The error is not caused by the existence of two blocks, but by the lack of unique identifiers (aliases) for them.
Correct answer

Make use of alias
Explanation

When defining multiple instances of the same provider, you must use the alias meta-argument for every instance except the default one. This allows you to reference specific provider configurations in your resource blocks (e.g., provider = aws.west). Without an alias, Terraform treats the second block as a duplicate definition of the default provider, resulting in a conflict.

Change the region from us to eu
Explanation

Changing the region value (e.g., from us-east-1 to eu-west-1) does not solve the underlying syntax error. The issue is a conflict in provider definitions, not the specific geographical location chosen. Even if you changed the region to Europe, Terraform would still see two conflicting default AWS provider blocks.

None of the Above
Explanation

Since Option B provides the exact technical solution required to fix the Terraform configuration error, "None of the Above" is not the correct choice.
Overall explanation

If you need to manage resources in different regions (or different AWS accounts) within the same Terraform run, you must define Multiple Provider Configurations.

To do this, you keep one default provider (optional, but recommended) and give all additional providers a unique name using the alias argument.

Corrected Code Example:

    # Default provider (resources go here if no provider is specified)
    provider "aws" {
      region = "us-east-1"
    }
     
    # Aliased provider (resources must explicitly reference this)
    provider "aws" {
      alias  = "west"
      region = "us-west-2"
    }
     
    # Resource using the default provider (us-east-1)
    resource "aws_instance" "foo" {
      ami           = "ami-123456"
      instance_type = "t2.micro"
    }
     
    # Resource using the aliased provider (us-west-2)
    resource "aws_instance" "bar" {
      provider      = aws.west  # <--- Reference the alias here
      ami           = "ami-654321"
      instance_type = "t2.micro"
    }

There is a need to rename a resource block in Terraform so that the current object is preserved, but managed under a new name.

Which Terraform command allows you to do this without destroying and recreating the resource?

terraform mv
Explanation

terraform mv is not a valid top-level Terraform command. While it looks intuitive because it resembles the Unix/Linux move command, Terraform requires state manipulation commands to be nested under the state subcommand (e.g., terraform state ...).
Correct answer

terraform state mv
Explanation

This command is specifically designed to move an item in the state file to a new address (name). By running this, you update the state file to map the existing real-world infrastructure to the new resource name in your configuration, ensuring Terraform does not try to destroy the old one and create a new one.

terraform plan
Explanation

terraform plan is a read-only command used to generate an execution plan and preview changes. It does not modify the state file; if you renamed a resource in your code and ran this, it would simply report that the old resource will be destroyed and a new one created, which is exactly what you want to avoid.

terraform plan mv
Explanation

mv is not a valid argument or flag for the terraform plan command. Terraform commands follow a specific syntax, and combining plan (a preview command) with mv (an action implying modification) is syntactically invalid and will result in an error.
Overall explanation

In Terraform, the State File is the source of truth that maps your configuration code (e.g., resource "aws_instance" "web") to the actual ID of the resource in the cloud (e.g., i-123456789).

When you simply rename a resource in your code (changing "web" to "database"), Terraform loses that link. It looks at the state file, sees "web" no longer exists in the code, and assumes it should be destroyed. It sees "database" is new in the code, and assumes it should be created.

The command terraform state mv is a State Refactoring tool. It tells Terraform: "Stop looking for 'web' and point that existing data to 'database' instead." This preserves the history and the actual infrastructure while allowing you to clean up your code naming conventions.

Note: In Terraform v1.1 and later, you can also use moved {} blocks within your configuration code to achieve this same result automatically during a plan/apply, which is often safer for teamwork than using the CLI command.

https://www.terraform.io/cli/commands/state/mv

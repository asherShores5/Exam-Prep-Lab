When you proceed to run terraform apply, what is likely to happen in this situation?

The instance type will be changed to t2.micro and again will be changed to t2.medium
Explanation

Terraform does not revert resources to the old state file version before applying new changes. It compares the current live state (fetched via API during the refresh phase) against the desired configuration. Since the live state (t2.medium) matches the desired configuration (t2.medium), no action is taken.

1 resource will be updated and you will see the message : Apply Complete ! Resources : 0 added, 1 changed, 0 destroyed
Explanation

This would only happen if the live infrastructure differed from the configuration file. Because the teammate manually updated the instance to match your configuration, Terraform detects that the goal has already been achieved. Therefore, it will not register a "change" action.
Correct answer

No resource will be updated and you will see the message: Apply Complete ! Resources : 0 added, 0 changed, 0 destroyed
Explanation

Upon running apply, Terraform performs an implicit refresh, detects that the actual instance type in AWS (t2.medium) already matches the configuration file (t2.medium), and updates its state file to match reality. It then reports that no changes are necessary to reach the desired state.

terraform apply will through an error
Explanation

Terraform is designed to handle "drift" (changes made outside of Terraform). It does not error out simply because a resource was modified manually; instead, it attempts to reconcile the state. Since the manual change aligns perfectly with the configuration, it resolves gracefully without errors.
Overall explanation

This scenario tests your understanding of the Terraform Lifecycle and State Refreshing.

When you execute terraform apply, the following sequence occurs:

    Refresh: Terraform queries the AWS API to get the current, live details of the resources. It discovers the instance is already t2.medium.

    Plan: It compares the live details against your .tf configuration files.

    Reconciliation: It realizes that Live State (t2.medium) == Desired Config (t2.medium).

Because the manual change made by your teammate accidentally "fixed" the drift before Terraform could, Terraform simply updates its local state file (terraform.tfstate) to reflect the new reality and reports that 0 changes are needed. This is a key feature of Terraform's declarative nature: it cares about the end state, not how it got there.

Based on the following Terraform Setting block, which provider versions satisfy the defined version constraint block?

    terraform { 
    required_providers { 
       aws = "~> 1.1.0" 
      }
    }

Correct selection

1.1.1
Explanation

This version satisfies the constraint because the major version (1) and minor version (1) match the requirement. The patch version (1) is greater than 0, making it a valid increment within the 1.1.x range. It falls safely between 1.1.0 and 1.2.0.

1.2.4
Explanation

The pessimistic operator ~> 1.1.0 locks the minor version to 1. This option attempts to increment the minor version to 2. Since 1.2.4 is greater than or equal to 1.2.0, it violates the upper limit of the constraint.
Correct selection

1.1.6
Explanation

Similar to option A, this version maintains the required major and minor versions (1.1). The patch version (6) is a valid increment over 0. As long as the version remains 1.1.x, it is accepted by the ~> 1.1.0 constraint.

1.2.2
Explanation

This version fails for the same reason as option B. The constraint ~> 1.1.0 only allows the rightmost specified number (the patch version 0) to increase. By changing the minor version from 1 to 2, this version exceeds the allowed range.
Overall explanation

The symbol ~> in Terraform is known as the pessimistic constraint operator. It is designed to allow the least risky updates (usually patch-level bug fixes) while preventing updates that might introduce breaking changes.

The behavior depends entirely on how many components you specify:

    If you specify three components (e.g., ~> 1.1.0): Terraform allows the patch version to increase, but locks the minor version. It allows 1.1.x but blocks 1.2.0.

    If you specify two components (e.g., ~> 1.1): Terraform allows the minor version to increase, but locks the major version. It allows 1.x but blocks 2.0.

In this specific scenario, because three components were provided (1.1.0), Terraform is looking strictly for 1.1.x versions. Therefore, only A and C are correct.

Enterprise Corp has different environment running in different AWS regions.

Every region in AWS has a different AMI ID for Linux OS and these AMI IDs keeps on changing at regular intervals from AWS side.

What is the best approach to create the EC2 instances that can deal with different AMI IDs based on regions?
Correct answer

Use data source aws_ami.
Explanation

This is the best practice for dynamic environments. The data "aws_ami" block allows Terraform to query the AWS API in real-time during the plan or apply phase. You can filter by name (e.g., "amzn2-ami-hvm-*"), owner (e.g., "amazon"), and architecture. This ensures that no matter which region you are deploying to, Terraform fetches the latest valid AMI ID automatically without manual updates.

Create a map of the region to ami id.
Explanation

While this is a valid syntactic approach in Terraform (using a variable map like us-east-1 = "ami-xyz"), it is a maintenance burden. Because the question states that AMI IDs are "regularly updated," you would have to manually update this map every time AWS releases a new patch. It fails the requirement for "automatic" updates.

Create different configuration files for different regions.
Explanation

This violates the DRY (Don't Repeat Yourself) principle and creates significant technical debt. Maintaining separate .tf files for every region just to change an AMI ID is inefficient. Like Option B, it also requires manual intervention to update the hardcoded IDs whenever AWS releases updates, failing the automation requirement.

None of the above
Explanation

Since Option A provides a native, efficient, and automated solution within Terraform to solve exactly this problem, "None of the above" is not the correct choice.
Overall explanation

The most robust way to handle AWS resources that vary by region and time (like AMIs) is to use Data Sources.

In Terraform, a resource creates something new, but a data source fetches information about something that already exists. By using data "aws_ami", you are telling Terraform: "Go ask AWS what the latest Amazon Linux 2 AMI is in the current region right now."

Here is how the code typically looks:

    data "aws_ami" "latest_linux" {
      most_recent = true
      owners      = ["amazon"]
     
      filter {
        name   = "name"
        values = ["amzn2-ami-hvm-*-x86_64-gp2"]
      }
    }
     
    resource "aws_instance" "web" {
      ami           = data.aws_ami.latest_linux.id
      instance_type = "t2.micro"
    }

This approach ensures that your infrastructure code remains static, but the actual AMI ID used is always dynamic and up-to-date with the specific region you are deploying into.

Question 8Skipped

Matthew wants to import a local module named database.

Which of the following configuration parameter can be used?

module "db" { source = "database"}
Explanation

This syntax implies that the source is a remote module hosted on the Terraform Registry, not a local file path. Without a path prefix like ./ or ../, Terraform interprets the string "database" as a namespace/name format (e.g., hashicorp/consul) or a registry alias, causing it to attempt a network lookup rather than looking locally.
Correct selection

module "db" { source = "./database"}
Explanation

This is the standard syntax for referencing a local module located in a subdirectory named "database" within the current working directory. The ./ prefix explicitly tells Terraform to look for the module on the local filesystem relative to the current configuration file, satisfying the requirement for a local import.
Correct selection

module "db" { source = "../database"}
Explanation

This is also a valid syntax for a local module, specifically one located in a sibling directory or a parent directory relative to the current configuration. Like option B, the ../ prefix explicitly indicates a local filesystem path. Note: Since the question implies the module is just named "database" without specifying its exact location relative to the root, both B and C are technically valid syntaxes for local modules, though B is the most common assumption for a direct subdirectory.

module "db" { source = "ftp:/database"}
Explanation

This syntax attempts to use a remote source via the FTP protocol. While Terraform supports various remote sources (like HTTP, Git, Mercurial, and S3), it does not natively support ftp:// as a module source protocol. Furthermore, the question specifically asks for a "local module," and a network protocol inherently implies a remote resource.
Overall explanation

In Terraform, the source argument is the only mandatory argument for a module block. It tells Terraform where to find the configuration files. To distinguish between a Local Module (on your computer) and a Remote Module (on the Internet/Registry), Terraform relies entirely on the prefix of the path.

    Local Paths: Must begin with ./ (current directory) or ../ (parent directory).

    Terraform Registry: Strings without path prefixes (e.g., aws/ec2-instance) are treated as Registry lookups.

    Remote URLs: Strings starting with git::, http::, s3::, etc., are treated as remote network locations.

Therefore, if you are referencing a folder on your own machine, you must use the relative path syntax (Option B or C).

Which of the following files are recommended to be excluded while committing Terraform Code to a Git Repository? (Choose 2)

variables.tf
Explanation

terraform.tfvars
Explanation

Correct selection

terraform.tfstate
Explanation

This file stores the mapping between your real-world resources and your configuration, often including sensitive data in plain text. Question 19Skipped

If HashiCorp Vault is integrated with Terraform, can it hide the secrets from the State files?

True
Explanation

While integrating Vault allows you to retrieve secrets dynamically during the terraform apply phase, Terraform's core design requires it to track the state of every resource it manages. If Terraform reads a secret from Vault to pass it to a resource (like a database password for an RDS instance), that value must be recorded in the state file so Terraform can detect future changes (drift).
Correct answer

False
Explanation

Even when using the Vault provider, if Terraform accesses a secret to configure a resource, that secret is stored in plain text within the .tfstate file. The integration secures the retrieval and storage of the secret at the source (Vault), but once Terraform consumes it, it becomes part of the state data. This is a known architectural characteristic of Terraform.
Overall explanation

The Terraform State file (terraform.tfstate) is the ultimate source of truth for your infrastructure.

    The Mechanism: When you use the Vault provider, Terraform authenticates with Vault and retrieves the secret.

    The Storage: Terraform passes that secret to the target resource (e.g., an AWS EC2 instance or SQL Database). To manage that resource later, Terraform writes the current configuration—including the secret values—into the state file in plain text.

    The Solution: Because Vault does not hide secrets from the state file, you must treat the state file itself as a sensitive artifact. You should always use Remote State (like S3 with encryption enabled or Terraform Cloud) to encrypt the state file at rest and strictly control who has access to read it.

In a terraform.tfvars file that is securely managed and only shared with authorized team members, but not committed to version control

Question 21Skipped

How do you reference to the below resource block code from a different Terraform resource block?

    resource "kubernetes_pod" "with_node_affinity" {
      metadata {
        name = "with-node-affinity"
      }

    with_node_affinity

Explanation

This is only the "local name" (or resource name) of the specific resource instance. In Terraform, using just the name is ambiguous because you could have different resource types (e.g., a pod, a service, or a variable) sharing the same local name. You must always qualify the name with the resource type to reference it correctly.

data.kubernetes_pod.with_node_affinity
Explanation

The prefix data. is exclusively used for Data Sources, which are used to fetch information about resources that already exist outside of Terraform or were created by a different configuration. Since the code provided is a resource block (creating a new resource), referencing it as a data source is syntactically invalid and will result in an error.

resource.kubernetes_pod.with_node_affinity
Explanation

While logical in English, Terraform syntax does not use the prefix resource. when referencing resources within the configuration. The keyword resource is only used when defining the block. When referencing it elsewhere, you omit the word "resource" entirely and start directly with the resource type.
Correct answer

kubernetes_pod.with_node_affinity
Explanation

This follows the standard Terraform reference syntax: <RESOURCE_TYPE>.<LOCAL_NAME>. The resource type is kubernetes_pod, and the local name defined in the block is with_node_affinity. This unique combination allows Terraform to locate the specific item in the state file and access its exported attributes (like .id or .metadata).
Overall explanation

In Terraform, every object you define has a specific "address" used to reference it in other parts of your code.

    Resources: Defined with resource "type" "name", referenced as type.name (e.g., aws_instance.web).

    Data Sources: Defined with data "type" "name", referenced as data.type.name.

    Variables: Defined with variable "name", referenced as var.name.

Question 24Skipped

You are part of a team responsible for managing infrastructure as code with Terraform. To connect to a remote backend such as AWS S3 or Azure Blob Storage, the team must provide access credentials (like API keys, tokens, or passwords). It’s crucial to prevent these sensitive secrets from being exposed or unintentionally checked into version control.

Given this context, which TWO methods are considered secure for storing the sensitive credentials Terraform needs to authenticate with a remote backend? (Select two.)

Directly specifying secrets within the backend block in your Terraform configuration files
Explanation

This is a security anti-pattern because the backend configuration block is part of the main Terraform code, which is almost always committed to version control (like Git). If you hardcode secrets here, they become permanently visible in the commit history to anyone with repository access, leading to immediate credential leakage.
Correct selection

Setting secrets as environment variables on the system or CI/CD pipeline running Terraform
Explanation

Terraform is designed to automatically look for specific environment variables (e.g., AWS_ACCESS_KEY_ID) to handle authentication without needing them written in code. This keeps secrets ephemeral and restricted to the runtime environment of the local machine or the CI/CD runner, ensuring they are never saved to disk or version control systems.
Correct selection

Storing secrets in a secure external secrets manager or configuration outside of Terraform, then referencing them as needed
Explanation

This approach delegates authentication to a dedicated security tool (like AWS CLI profiles, HashiCorp Vault, or Azure Key Vault) rather than Terraform itself. By configuring the backend to use credentials stored in a standard, secure location on the host machine (like ~/.aws/credentials), Terraform can authenticate securely without the code ever knowing the actual secret values.

Defining secrets in a separate variable file (e.g., secrets.tfvars) and including it with your Terraform commands
Explanation

While better than hardcoding, the Terraform backend block specifically does not support interpolation or variables; it requires static values or external configuration. Therefore, you technically cannot pass a .tfvars variable into the backend configuration block to authenticate the backend itself; this method only works for provider or resource configuration, not backend initialization.
Overall explanation

When working with Terraform, the "Backend" configuration is unique because it initializes before Terraform can even load your variables. This creates a "chicken-and-egg" problem: you cannot use standard Terraform variables (like var.my_password) inside the backend { ... } block.

Therefore, to secure backend credentials, you must rely on methods that exist outside of the Terraform code itself. The two industry-standard ways to do this are:

    Environment Variables: Injecting secrets into the shell or CI/CD pipeline at runtime.

    External Configuration Files: Relying on the cloud provider's default credential files on the host machine (partial configuration), so the Terraform code remains generic and secret-free.

Never commit secrets to Git. Once a secret is pushed to a repository, it is considered compromised and must be revoked immediately.
